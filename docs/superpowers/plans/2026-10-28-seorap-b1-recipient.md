## 왜 이 조각인가

1. **보호장치:** 지금은 서랍에 들어올 때마다 문자 OTP를 받아야 한다. 첫 인증 뒤 PIN으로 들어오게 해서, 링크만으로는 열리지 않으면서도 매번 문자를 기다리지 않게 한다.
2. **흐름 완성:** 지금 [전달하기]를 누르면 받는 분에게 `/f/{토큰}` 링크가 가지만, 그 주소를 열 화면이 없다(404). 이 조각이 끝나면 **"산 사람이 가족에게 보내고, 가족이 열어서 실시한다"**는 흐름이 처음부터 끝까지 이어진다.

외부 회신(IT·상담센터)을 기다리지 않는다.

## 만드는 것 ①: PIN과 경고

| # | 무엇 | 동작 |
|---|---|---|
| P1 | **PIN 설정** | OTP를 처음 통과하면 숫자 6자리 PIN을 두 번 입력해 정한다. 111111·123456·654321 같은 숫자는 받지 않는다 |
| P2 | **PIN 입장** | PIN을 정한 서랍은 링크를 열면 PIN 입력 화면이 먼저 나온다. 문자를 보내지 않는다 |
| P3 | **PIN을 잊었어요** | OTP로 다시 인증하고 PIN을 새로 정한다. 5번 틀리면 PIN 입장이 잠기고 같은 길로 안내한다 |
| P4 | **보내기 전 경고** | 전달 확인 화면과 링크 복사 모두에 "링크를 받은 분은 누구나 검사를 시작할 수 있어요. 잘못 보내거나 공유해 검사가 진행되면 환불·재발급이 안 돼요" |

서버 함수 2개를 추가한다: `pin/set`(OTP 직후에만), `pin/verify`(틀린 횟수·잠금). 진입 함수는 "PIN이 있는 서랍인지"를 함께 돌려준다.

## 만드는 것 ②: 받는 분 화면

| # | 무엇 | 동작 |
|---|---|---|
| 1 | **받는 분 1매 화면** `/f/{토큰}` | 서랍 워드마크, "홍\*동님이 보낸 심리검사예요", 검사명, [실시하기], 더보기 > [코드 보기(PC)], 문의처, 사칭 주의 한 줄. 보낸 사람 번호와 같은 주문의 다른 검사는 보이지 않는다 |
| 2 | **열어 봄 기록** | 페이지를 여는 것만으로는 기록하지 않는다(카카오톡 미리보기 봇이 먼저 열기 때문). [실시하기]나 [코드 보기]를 누른 순간 기록한다. 기록되면 구매자 서랍의 그 줄이 "받는 분이 열어 봄"으로 바뀐다 |
| 3 | **실시 후 다시 열기** | 한 번 실시한 뒤 링크를 다시 열면 버튼이 [이어서 하기]로 바뀐다 |
| 4 | **코드 노출 연동** | 받는 분이 코드를 보면 구매자 서랍에서 그 줄의 [다른 분께]가 사라진다(이미 있는 규칙을 받는 분 쪽에서도 지킨다) |
| 5 | **링크 무효 화면** | 사유별 문구: 다른 분께 다시 보냄 / 전달 취소 / 검사 취소 / 그 밖(번호 변경·관리자·만료) |
| 6 | **상태 화면 보완** | 기존 상태 화면(없는 주소·무효 링크·세션 만료·장애)을 점검하고, 받는 분 무효 사유를 추가 |
| 7 | **도움말** `/help` | 문자가 안 와요 / 링크를 잃어버렸어요 / 취소하고 싶어요 / 결과는 어디서 보나요 / 이런 문자는 서랍이 보내지 않아요. 문의처는 설정값 |

서버 함수 3개를 추가한다: `forward/page`(화면 정보, 기록 없음), `forward/launch`(열어 봄 + 실시 기록 → 검사 주소), `forward/code`(열어 봄 + 코드 노출 기록 → 코드).

## 이번에 넣지 않는 것

- 받는 분 OTP(설정 `forward_otp_required`): 기본값이 꺼짐이라 자리만 둔다
- 받는 분 쪽 상담 동의(counsel-form §5-4): 상담 조각(B2)에서 상담 원장과 함께
- 실제 알림톡 발송: 가짜 발신함(`/dev/outbox`)으로 링크를 받는다
- 상담 "선 검사" 순서와 응시 완료 판정: 나중에 (지금은 선 상담 잠금만)

## 건우님이 눈으로 확인할 것

**PIN**
- A. 서랍 링크 → OTP → PIN 설정 화면이 자연스럽게 이어지는가
- B. 로그아웃하고 같은 링크를 다시 열면 PIN만으로 들어가지는가 (발신함에 새 문자가 없어야 함)
- C. [PIN을 잊었어요] → OTP → 새 PIN으로 들어가지는가
- D. 전달 확인 화면과 링크 복사에서 경고 문구가 잘 보이고, 겁주지 않으면서 분명한가

**받는 분**
1. 구매자 서랍에서 1매를 전달한다 → 가짜 발신함에서 받는 분 링크를 연다
2. 받는 분 화면이 휴대폰 폭에서 자연스러운가: 문구, 버튼 위치, 보낸 사람 표시
3. 링크를 열기만 했을 때 구매자 서랍은 아직 "안 열어 봄"인가 → [실시하기]를 누르면 "열어 봄"으로 바뀌는가
4. 다시 열면 [이어서 하기]로 바뀌는가
5. 받는 분이 [코드 보기]를 누르면 구매자 쪽 [다른 분께]가 사라지는가
6. 구매자가 [다른 분께] 또는 전달 취소를 하면, 처음 받는 분의 링크가 사유에 맞는 무효 화면으로 가는가
7. 도움말 문구가 고객에게 겁주지 않고 짧은가
8. (미리보기 배포 후) 실제 휴대폰 **카카오톡 인앱 브라우저**에서 받는 분 링크가 열리는가

## Claude가 테스트로 확인할 것 (화면에 안 보이는 규칙)

- PIN 원문이 DB·응답·로그 어디에도 없다. PIN 설정은 방금 OTP를 통과한 세션에서만 된다
- PIN 5번 틀리면 맞는 PIN도 거부하고, 서랍마다 따로 센다
- 토큰이 틀리거나 무효·만료면 정보·코드를 내보내지 않는다
- 페이지 조회(`forward/page`)는 아무것도 기록하지 않는다
- 받는 분 토큰으로는 그 1매만 볼 수 있다(같은 주문의 다른 발송권, 보낸 사람 번호 접근 불가)
- 무효화와 실시가 동시에 일어나도 무효된 링크로 코드가 나가지 않는다(DB 잠금 아래 다시 검사)
- 응답·로그에 토큰·코드·번호 원문이 남지 않는다
- 화면 코드에 직접 쓴 문장이 없다(모든 문구는 문구 사전)

## 순서

1. PIN: DB 칸·서버 함수 2개 + 테스트 → 진입·PIN 화면
2. 보내기 전 경고 문구 (문구 사전 + 전달 확인·링크 복사)
3. 받는 분 서버 함수 3개 + 테스트 (Plan A의 구매자 쪽 실시·코드 함수와 같은 방식)
4. 받는 분 화면 + 무효 화면 + 테스트
5. 도움말, 상태 화면 보완
6. 로컬에서 시드 S1(공구 3매, 1매 전달됨)으로 전체 흐름 점검 → **건우님 로컬 검수**
7. 피드백 반영 → 미리보기 배포(일시정지된 Supabase 미리보기 재시작 필요할 수 있음) → **휴대폰 검수(8번)**
8. 결정 로그·build-spec에 검수 중 바뀐 점 기록
