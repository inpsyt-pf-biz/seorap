# 시안 가정 (MVP-0 ~ MVP-2, 검사 현황·진행 단계)

시안은 아래 기본값으로 만들었습니다. 답이 다르면 "바뀌는 곳"만 고칩니다.

| # | 가정 | 기본값 | 다르면 바뀌는 곳 |
|---|---|---|---|
| M1 | 센터 전문 분야(구 카테고리) | 발달 · 정서 · 청소년 · 학습 · 가족 (5종, 여러 개 선택). 대상의 "아동·청소년"과 전문 분야의 "청소년"은 다른 축이다 | 마이그레이션 CHECK, `core/centers.ts`, `core/copy.ko.ts`, 태그 색(`web/src/theme/admin.ts`). `core/centers.test.ts`가 DB와 화면 목록을 대조 |
| M2 | 센터 상태 | 입점 준비 · 운영 중 · 신규 배정 중지 · 계약 종료 (4종). 목록에서는 운영 중이 아닌 센터만 이름 아래에 표시 | 같음 |
| M3 | 목록의 "지역" | 센터가 있는 곳 1군데(시·도 + 구·시, 예: 서울 강남). 구·시는 직접 입력 | 구·시를 목록에서 고르게 하려면 행정구역 목록 추가 |
| M4 | 상담 가능 지역 | 시·도 여러 개. 목록에는 안 보이고 상세·수정 화면에만 있다. 예약을 센터에 배정할 때 쓴다 | - |
| M5 | 상담 완료/배정 | 상담 장부에서 센다. 배정은 취소를 뺀 건수, 완료는 상담 완료 건수(MVP-1부터) | `counsel.center_stats` 뷰 |
| M6 | 센터는 지우지 않는다 | 끝난 센터는 "계약 종료"로 남긴다. 삭제 기능 없음 | 삭제 함수 추가 |
| M7 | 기관명은 겹치지 않는다 | 대소문자를 무시하고 같은 이름 등록을 막는다 | `centers_name_unique` 인덱스 |
| M8 | 연락처 형식 | 숫자와 `-`로 8~20자. 대표번호는 유선·070도 받고, 휴대폰 형식으로 바꾸지 않는다 | 마이그레이션 CHECK, `validateCenterInput` |
| M9 | 센터 정보 관리 권한 | 인싸이트 관리자만 등록·수정. 담당자는 보기만 | `counsel.role_caps` 한 줄 |
| M10 | 인싸이트 본사 | 센터 표의 한 행. 목록에 보이지 않고 화면에서 고칠 수 없다 | `listCenters`, `rpc_update_center` |
| M11 | 변경 이력 | 마지막 수정 시각과 version만 남긴다. 누가 무엇을 바꿨는지는 예약 원장(MVP-1)부터 | 이력 표와 트리거 추가 |
| M12 | 담당자 | 센터당 대표 담당자 1명. 여러 명은 센터 직원 레코드(MVP-2)에서 | 센터 직원 표 |
| M13 | 지도 서비스 | 네이버 클라우드 Maps. 시안은 Mind-Connect의 키를 같이 쓴다 | `web/src/lib/naverMaps.ts` 하나만 바꾼다 |
| M14 | 센터 위치 | 등록·수정 화면에서 지도를 눌러 찍는다(주소로 자동으로 찾지 않음). 국내 좌표만 받는다 | 주소 → 좌표 변환을 붙이면 위치 찍기를 자동으로 채운다 |
| M15 | 지도 동그라미 | 전국 화면은 시·도별 센터 수(소재지 기준). 동그라미 자리는 겹치지 않게 정한 표시용 자리다. 확대 10단계부터 센터별 핀 | `core/geo.ts` 의 `SIDO_ANCHORS`, `PIN_ZOOM` |
| M16 | 센터 대상 | 영유아 · 아동·청소년 · 성인 (여러 개 선택). 기획 문서 Step 1 필터의 "상담 유형" | 마이그레이션 CHECK, `core/centers.ts` |
| M17 | 운영 시간 | 자유 입력 한 줄(100자). 예약 가능 시간을 시스템이 판단하지 않으므로 요일별 칸으로 나누지 않는다 | 요일별 구조로 바꾸려면 칸 추가 |

## MVP-1 (구매 건 · 배정)

| # | 가정 | 기본값 | 다르면 바뀌는 곳 |
|---|---|---|---|
| M18 | 구매 구분 | 검사 메인 · 상담 메인 · 협찬 · 공동구매 (현행 구글폼 신청서 4종) | 마이그레이션 CHECK, `core/purchases.ts` |
| M19 | 상담 상태 | 미배정 → 예약 요청 → 예약 확정 → 상담 완료, 이탈은 상담 불가 · 취소. "예약 요청"은 센터에 배정되어 예약을 기다리는 상태 | 같음 |
| M20 | 배정·다시 배정 | 미배정·예약 요청·상담 불가 회차만 바꾼다. 예약 확정·상담 완료·취소 회차는 건너뛴다. 다시 배정하면 예약 일시를 지운다 | `rpc_assign_sessions`, `ASSIGNABLE_STATUSES` |
| M21 | 배정할 수 있는 센터 | 운영 중인 센터만. 입점 준비·신규 배정 중지·계약 종료 센터와 본사는 DB가 거부 | `rpc_assign_sessions` |
| M22 | 구매 1건의 상담 횟수 | 직접 등록·시트 가져오기는 1회. 네이버 주문은 주문 수량 × 상품 목록표의 1단위당 횟수(기본 1) | 등록·가져오기 함수, `naver_product_types.sessions_per_unit` |
| M23 | 민감정보·마케팅 정보 | 복용 약물·진단명, 결과지 링크는 `application_sensitive`, 알게 된 경위는 `application_marketing`에 따로 둔다. 지금은 본사만 읽는다. 센터 계정이 생기면 민감정보는 배정된 센터만, 마케팅은 본사만 | 두 표의 행 단위 권한 |
| M24 | 시트에서 같은 줄 판정 | 신청서 종류 + 응답 시각 + 연락처 + 이름이 같으면 같은 줄. 다시 가져와도 한 건만 남는다 | `core/sheetImport.ts`의 `source_key` |
| M25 | 시트의 담당자 칸 | 예약전화 완료 체크·상담 예약 일정·관리자 메모는 관리자 메모에 붙인다(구매 건에 붙을 때 덧붙임). 상담 상태는 바꾸지 않는다 | `toImportRow`, `_attach_application` |
| M26 | "상담 종료" 체크된 줄 | 기본으로 건너뛴다(가져오기 창에서 끌 수 있다) | 가져오기 창 체크 상자 |
| M27 | 검사 실시 칸 | 서랍 연결(Step 0) 전까지 "서랍 연결 후"로 표시 | 서랍 검사 진행 상태를 읽어 채운다 |
| M28 | 신청서 날짜 | 폼 응답 시각. 직접 등록해서 응답 시각이 없으면 등록한 날 | 목록 "신청서" 칸 |
| M29 | 상태별 건수 칩 | 검색·구분·센터·검사 거르기를 적용한 결과로 센다. 칩을 눌러도 다른 칩 숫자는 그대로 | `PurchasesListPage` |

## MVP-2 (상담 진행 · 메모 · 신청서 대기함 · 센터 세부)

| # | 가정 | 기본값 | 다르면 바뀌는 곳 |
|---|---|---|---|
| M40 | 상태마다 할 수 있는 일 | 미배정: 취소 / 예약 요청: 예약 확정·상담 불가·취소 / 예약 확정: 예약 변경·상담 완료·상담 불가·취소 / 상담 불가: 취소(또는 다른 센터로 다시 배정) / 상담 완료·취소: 없음 | `rpc_update_session`, `core/sessions.ts` (시험이 둘을 대조) |
| M41 | 꼭 받는 값 | 예약 확정·변경은 예약 일시, 예약 변경·상담 불가·취소는 사유(500자). 상담 방식(대면·비대면)은 고르지 않아도 된다 | 같음 |
| M42 | 되돌리기 | 상담 완료·취소는 되돌리지 않는다. 잘못 바꿨으면 메모로 남기고 새 회차는 직접 등록으로 만든다 | 되돌리기 함수 추가 |
| M43 | 진행 바꾸기 권한 | 본사 관리자·담당자. 센터 공용 계정은 MVP-3에서 예약 일시 입력·상담 완료만 더한다 | `role_caps`의 `session.manage` |
| M44 | 건 메모 | 구매 건 단위, 1000자, 누가 언제 남겼는지 보인다. 고치거나 지울 수 없다. 지금은 본사만 읽고 쓴다 | `purchase_notes`, `note.write` |
| M45 | 시트 줄 → 구매 건 | 상품주문번호가 있고 그 번호의 구매 건에 신청서가 없으면 바로 붙인다. 그 밖(번호 없음·번호 틀림·이미 신청서 있음)은 대기함 | `rpc_import_applications` |
| M46 | 대기함 후보 | 신청서가 없는 구매 건 가운데 연락처 끝 4자리(3점)·가린 이름(2점)이 하나라도 맞는 건. 구분 일치·결제 뒤 14일 안 신청이 1점씩 더한다. 3건까지 | `core/inbox.ts` |
| M47 | 대기함 처리 뒤 | 신청서 내용을 지우고, 같은 줄을 다시 가져오지 않도록 기록만 남긴다. 새 구매 건으로 만들 때 신청자가 적은 상품주문번호를 달아 두어 나중에 같은 네이버 주문이 오면 합친다 | `application_inbox` |
| M48 | 붙일 때 구분 | 구분이 비어 있는(미분류) 구매 건에 신청서를 붙이면 신청서 종류를 구분으로 쓴다 | `_attach_application` |
| M49 | 상담사 | 센터별 이름·메모·활동 여부만. 상담 회차와 잇는 것은 센터 계정 뒤에 정한다 | `center_counselors` |
| M50 | 목록의 한 줄 | 회차가 여럿이면 끝나지 않은 첫 회차를 대표로 보이고 "완료 n/전체 m회"를 붙인다. 목록에서 배정하면 고른 구매 건의 배정할 수 있는 회차가 모두 같은 센터로 간다 | `mainSession`, `assignableSessionIds` |

## 검사 현황 · 진행 단계

| # | 가정 | 기본값 | 다르면 바뀌는 곳 |
|---|---|---|---|
| M51 | 검사를 묶는 기준 | 구매자 아래에, 같은 네이버 결제(주문번호)로 함께 산 검사를 모은다. 상품주문번호가 같은 상담 구매 건이 있으면 그 건(패키지), 없으면 같은 주문번호의 먼저 생긴 상담 구매 건. 따로 결제한 검사는 따로 | `rpc_sync_purchase_tests` |
| M52 | 실시 상태 | 서랍 검사 코드 값 그대로: 미실시 / 실시 중(응시를 시작했지만 끝내지 않음) / 실시 완료 / 삭제됨(세지 않음) | `purchase_tests.exam_status`, `core/exams.ts` |
| M53 | 응시자 이름·결과지 | 인싸이트 검사결과 API에서 받는다. 연결 전에는 "결과 연결 후". 결과지는 https 주소만 받고, 실시 완료이면서 결과지가 있을 때만 연다. 지금은 본사만 읽고, 센터에 어디까지 보일지는 3단계 때 정한다 | `purchase_tests`, `ExamsTab` |
| M54 | 진행 단계 | 구매 → 신청서 작성 → 센터 배정 → 상담 예약 → 검사 실시 → 상담 완료 → 보고서 제출. 순서를 강제하지 않고, 뒤 단계가 끝났는데 앞 단계가 비면 '누락'. 검사가 연결되지 않은 건과 보고서(3단계 전)는 세지 않는다 | `core/progress.ts` |
| M55 | 멈춘 회차 | 취소는 끝나지 않은 단계를 모두, 상담 불가는 배정 뒤 회차 단계를 멈춤으로 보인다(상담 불가는 다시 배정하면 이어진다). 진행 단계는 취소되지 않은 회차마다 보인다 | 같음 |
| M56 | 목록의 검사 실시 칸 | 서랍 연결 후(검사 없음) / 미실시 / 실시 중 / 완료 m/n / 실시 완료 | `examSummaryText` |
